## Шаг 0. Каркас проекта и качество (кабан-кволити)

**Цель:** пустой, но рабочий Python-проект с инструментами качества до первого кода.

**Задачи:**
1. Каркас через uv: Python 3.12+, пакет `src/ai_coach/`, `tests/`, `pyproject.toml`. Пустые модули по архитектуре: `garmin/`, `store/`, `sync/`, `goals/`, `plan/`, `load/`, `workouts/`, `cli/`, `mcp_server/`.
2. Зависимости: garminconnect ≥0.3, typer, mcp, pydantic; dev — pytest и инструменты качества.
3. Инструменты качества выбирает кабан-кволити: линтер/форматтер, проверка типов, мёртвый код, дубли, покрытие с порогом, мутационное тестирование.
4. Мутационные тесты запускаются отдельной командой фоном вне агента; сессия только читает отчёт (правило из проверки по деньгам).
5. `.gitignore`: `.venv`, `*.db`, токены Garmin, `spikes/out/`, любые выгрузки с личными данными.
6. Одна команда, которая гоняет все проверки (например, `make check` или `uv run …`) — описать в README.

**Готово, когда:**
- `uv sync` и команда проверок проходят на чистом клоне.
- Есть один тривиальный тест, порог покрытия включён.
- Мутационный прогон запускается и выдаёт отчёт.
- В репо нет и не может попасть `*.db` и токены (проверить `git status` после создания пробных файлов).

## Шаг 1. Спайк Garmin

**Цель:** ответ «работает / не работает» по каждому пункту ниже на реальном аккаунте и FR970. Это одноразовые скрипты, а не продакшен-код.

**Правила:**
- Скрипты в `spikes/garmin/`, вывод в `spikes/out/` (в `.gitignore`).
- Логин и пароль Garmin вводит пользователь сам: скрипт спрашивает через `getpass`, запуск через `! uv run …` в терминале. В чат и в файлы креды не попадают.
- Токены: `~/.config/ai-coach/garmin/`, права 600, вне репозитория.
- Логинов минимум: один полный логин, дальше только переиспользование токенов (риск блокировки аккаунта).
- Ничего не отправлять на часы без подтверждения пользователя в терминале.

**Проверки:**
| # | Что | Критерий «работает» |
|---|---|---|
| 1 | Логин | Логин проходит (с MFA, если она включена — заодно выяснить, включена ли). Токены сохранены, повторный запуск входит без пароля. |
| 2 | Метрики за 30 дней | Сон, HRV, Body Battery, стресс, Training Readiness приходят с FR970. Зафиксировать, какие поля пустые или за пейволлом Connect+. |
| 3 | Активности | Список активностей за 30 дней; у силовой — подходы, повторы, веса. |
| 4 | Силовая на часы | Тренировка с упражнениями и весами создаётся, загружается, планируется на дату. Пользователь подтверждает, что она на часах и идёт с подсказками упражнений. Сохранить эталонный JSON. |
| 5 | Растяжка на часы | То же для утренней растяжки (какой тип тренировки принимает FR970). |
| 6 | Бег / вело / плавание | По одной простой структурированной тренировке каждого типа загружается и видна на часах. |
| 7 | Удаление | Загруженные тестовые тренировки удаляются из Garmin Connect через API. |
| 8 | Ручной экспорт | Пользователь делает экспорт данных Garmin Connect (zip); скрипт находит в нём сон, HRV и FIT активностей. |

Если пункт 4 не работает — по решению пользователя силовая отправляется текстом (развилка 5 в архитектуре); спайк фиксирует, как именно.

**Результат:** `docs/spike-garmin-<дата>.md` — таблица пунктов 1–8 с результатом, найденные ограничения, эталонные форматы (без личных данных), что меняется в архитектуре. Личные данные и сырые ответы — только в `spikes/out/`.

## Шаг 2. Хранилище (`store/`)

**Цель:** SQLite-база со схемой из архитектуры и миграциями.
1. SQL-миграции в пакете, номер версии в БД, применение при открытии; путь к БД по умолчанию вне репо (`~/.local/share/ai-coach/coach.db`), переопределяется.
2. Таблицы: daily_metrics, activities, strength_sets, weight_log, goals, phases, goal_events, planned_workouts, plan_actual, food_log, sync_log. В каждой записи из Garmin — `raw_json`.
3. Тонкий слой доступа (функции/репозитории) — только то, что нужно шагам 3–8, без ORM.

**Готово, когда:** миграции применяются на пустой и на уже мигрированной базе; upsert по естественному ключу (дата / id активности) не плодит дубли; тесты и `make check` зелёные.

## Шаг 3. Синхронизация и импорт (`garmin/`, `sync/`, `cli`: `login`, `sync`, `import`)

**Цель:** данные Garmin в базе, идемпотентно.
1. `garmin/`: обёртка над garminconnect — вход по токенам (`~/.config/ai-coach/garmin/`, 600), `coach login` — единственное место полного логина (getpass). 429 / протухшие токены → понятная ошибка, база не трогается.
2. `coach sync [--days N]`: метрики (сон, HRV, BB, стресс, readiness), активности, подходы силовой (с `wktStepIndex`); запись в `sync_log`.
3. `coach import <fit|zip>`: FIT активностей; разбор полного экспорта — по итогам п.8 спайка; шаг 3 закрывается без него, разбор доделывается отдельно, когда придёт архив.

**Готово, когда:** повторный sync не меняет базу; пропуски метрик за день не ломают sync; ошибка авторизации оставляет кэш целым; фикстуры из реальных ответов.

## Шаг 4. Цели и фазы (`goals/`)

**Цель:** цели пользователя, фазы (proposed/accepted), история изменений.
1. CRUD целей, предложение фазы (черновик) и её принятие пользователем.
2. `goal_events`: любое изменение пишется событием; состояние целей на любую дату.

**Готово, когда:** «какие цели были на дату X» отвечает верно после серии изменений.

## Шаг 5. Тренировки и отправка (`workouts/`, `plan/`, `cli`: `push`, `status`)

**Цель:** план недели → тренировки на часах.
1. Сборка JSON по эталонам спайка: силовая (вес в кг, свой код вместо `create_strength_set`), растяжка (`mobility` + `WARM_UP/STRETCH_*`, техника по-русски в `description`), бег/вело/плавание.
2. planned_workouts: draft → approved → pushed.
3. `coach push <id>`: печатает, что отправляет, y/N, загрузка + план на дату; повторный push заменяет только свою тренировку (unschedule + delete старой) — после отдельного y/N с показом, что удаляется. `coach status` — что запланировано/отправлено.

**Готово, когда:** сериализация = эталоны спайка (тест сравнения); push без «y» ничего не шлёт и ничего не удаляет; ручная проверка одной тренировки на часах пользователем.

## Шаг 6. План/факт и нагрузка (`load/`)

**Цель:** сопоставление плана и факта, CTL/ATL.
1. plan_actual: сопоставление по дате и типу, у силовой — по `wktStepIndex`; случаи «пропуск / лишняя / другая тренировка».
2. Свой TSS → CTL/ATL (развилка 3A).

**Готово, когда:** три случая план/факт покрыты тестами; CTL/ATL совпадают с ручным расчётом на фикстуре.

## Шаг 7. MCP и скиллы (`mcp_server/`, скиллы)

**Цель:** тренер в Claude Code.
1. MCP (stdio): чтение агрегатов (без raw_json, лимит строк/размера), `get_morning_snapshot`; запись только черновиков (план, фаза). Отправки на часы нет.
2. Скиллы /coach-morning (Sonnet/Haiku), /coach-plan (Sonnet): логика в промптах, цифры из MCP. /coach-morning даёт и текстовые рекомендации по восстановлению (массаж, баня).

**Готово, когда:** тест, что через MCP нельзя отправить на часы; ответы в пределах лимитов; пользователь прогнал утренний разбор и план недели.

## Шаг 8. Вес и питание (`cli`: `weight`, `food`; скилл /coach-food)

**Цель:** вес и еда в базе.
1. `coach weight <кг>`, `coach food "<текст>"` — только сохраняют (без LLM в Python).
2. /coach-food (Sonnet/Haiku) раз в день пачкой считает КБЖУ и пишет через MCP-черновик.

**Готово, когда:** записи сохраняются и видны в утреннем снапшоте; пользователь прогнал /coach-food на дне еды.

## Шаг 9. Импорт zip-экспорта Garmin (`sync/`, `cli`: `import <zip>`)

**Цель:** история из ручного экспорта Garmin Connect в базе, без сети, идемпотентно.

Разбор архива (2026-10-07, без личных данных):
- Активности: `DI_CONNECT/DI-Connect-Uploaded-Files/UploadedFiles_*_Part*.zip` — вложенные zip, 9201 FIT; активности — только `file_id.type == activity` (344 шт.), остальное (monitoring_b, числовые типы, segment_list) пропускается. В именах FIT нет `activityId`: он берётся из `DI-Connect-Fitness/*_summarizedActivities.json` (`[0].summarizedActivitiesExport[]`) по совпадению `session.start_time` (UTC, секунды) с `startTimeGmt` (мс). Совпало 344 из 344; без совпадения — пропуск с подсчётом.
- Сон: `DI-Connect-Wellness/*_sleepData.json` (список ночей, с 2024-11): `calendarDate`, `sleep_seconds` = deep + light + rem (+ поля, которых нет, — 0), `sleep_score` = `sleepScores.overallScore` (есть не у всех ночей).
- HRV: `DI-Connect-Wellness/*_healthStatusData.json` (с 2025-12): `calendarDate`, в `metrics[]` элемент `type == "HRV"` → `hrv_last_night` = `value`, `hrv_status` = `status`. Недельного среднего нет.
- Остальное содержимое архива не читается.

Решения пользователя (2026-10-07): импортировать активности + сон + HRV; **sync главнее** — экспорт только добавляет отсутствующие дни/активности и не меняет существующие строки; история — вся.

**Задачи:**
1. `coach import <path>`: `.zip` → разбор экспорта, иначе как сейчас (FIT). `--id` для zip запрещён.
2. Активности через существующий разбор FIT (`sync/fit_import.py`), включая подходы силовой; `raw_json` — сообщения FIT как сейчас.
3. `daily_metrics` из сна и HRV: один ряд на дату, сон и HRV одного дня сливаются; `raw_json` — исходные элементы экспорта.
4. Итог печатью: сколько активностей/дней добавлено, пропущено (уже в базе), не сопоставлено; запись в `sync_log`.
5. Архив целиком в память не распаковывается на диск; в логи и ошибки не попадают имена файлов с email.

**Готово, когда:** повторный импорт того же zip ничего не меняет; существующие строки из sync не трогаются; фикстура — маленький синтетический zip той же структуры (обезличенный); тесты и `make check` зелёные; пользователь прогнал импорт на своём архиве.

## Шаг 10. Режим тренера (одна точка входа)

**Цель:** вместо ручного вызова скиллов — разговор с тренером одной командой `тренер` (`claude --agent coach` в папке проекта).

Решения пользователя (2026-10-07): запуск словом `тренер`; самочувствие хранится в базе (дата, оценка 1–5, текст); пересчёт плана при отклонениях (бэклог) закрывается в этом шаге.

Поведение: при старте `coach sync` → приветствие и сводка (восстановление, план на сегодня, факт вчера) → вопрос о самочувствии и еде (запись через `coach food`, КБЖУ как в /coach-food) → адаптация плана черновиками, рекомендации на день/неделю. Логика переиспользует /coach-morning, /coach-plan, /coach-food. Отправка на часы — только пользователем (`coach approve/push`).

Детальный план — папа-кабан (2026-10-07): миграция 0006 `wellbeing_log`, `coach feel`, MCP `get_wellbeing`/`get_deviations` (+ разделы в snapshot), `load/deviations.py`, агент `.claude/agents/coach.md` (читает SKILL.md трёх скиллов), `bin/trener` + `make install-trener`, `.claude/settings.json` (allow sync/food/feel/status, deny approve/push), пересчёт плана в /coach-plan. Первым — ручной спайк `claude --agent` и tools с MCP-именами.

Решения пользователя по плану (2026-10-07, «по рекомендациям»):
1. Плохое восстановление: самочувствие ≤ 2, readiness < 33, HRV LOW/UNBALANCED, ATL − CTL > 15, сон < 6 ч — константы модуля.
2. Вело только сб/вс — жёсткая проверка в `create_draft_workout` + промпты.
3. Самочувствие пишется через CLI `coach feel` из агента, MCP только читает.
4. Запуск: symlink `~/.local/bin/тренер` → `bin/trener`.
5. `coach sync` при каждом старте (без порога по времени).
6. Несколько оценок в день, записи только добавляются (основная — последняя).
7. Горизонт пересчёта — до конца текущей недели (в сб/вс — плюс следующая).

Проверка по деньгам (кабан-тесть, 2026-10-07): ок — около $0.25 за сессию на Sonnet по ценам API, по подписке без доплаты. Решения пользователя:

- тренеру нужна история за месяц (snapshot не ужимать до 7 дней);

- подписка Max 5, несколько запусков в день допустимы.
Сокращения тестя без возражений: краткий итог `coach sync`, пересчёт только при порогах, в агенте только MCP ai-coach и Bash для `coach`.

Спайк `claude --agent` (2026-10-07): агент из `.claude/agents/*.md` подхватывается, `model: sonnet` работает; поле `tools` с MCP-именами (`mcp__ai-coach__get_goals`) и `Bash` ограничивает набор инструментов; MCP ai-coach подключается из local-конфига проекта. Без allow в настройках MCP и Bash спрашивают разрешение; allow `Bash(uv run coach status:*)` пропускает, deny `Bash(uv run coach push:*)` блокирует — схема `.claude/settings.json` подтверждена. ## Шаг 11. Профиль спортсмена

**Цель:** тренер знает пользователя — без этого рекомендации не юзабельны (отзыв пользователя после первого прогона `тренер`, 2026-10-07: «он меня не знает (вес, рост, пол, потребности, цели)… нужен какой-то жёсткий профиль»).

Детальный план — папа-кабан (2026-10-07): журнал `profile_log` (ключ-значение, только добавление, миграция 0007), `profile/service.py` (белый список ключей, `missing`), `profile/nutrition.py` (BMR/TDEE/КБЖУ), профиль из Garmin при `coach sync`, CLI `coach profile show/set` и `coach goal add/list/done/cancel`, MCP `get_profile` + раздел `profile` в snapshot (не ужимается), опрос тренером при пустом профиле, учёт в /coach-plan, /coach-food, /coach-morning.

Решения пользователя (2026-10-07, «все по рек.»):
1. Хранение — журнал с историей (профиль на дату).
2. Ручное значение главнее Garmin; Garmin — только если ручного нет.
3. Заполнение — опрос тренером при пустом профиле + `coach profile set` для правок.
4. КБЖУ: Mifflin-St Jeor × коэффициент активности + калории тренировок; дефицит 15–20% (не ниже BMR), профицит 10%; белок 1.8–2.2 г/кг; ручное переопределение `kcal_target`.
5. Расписание — свободный текст, учитывается в промпте (жёсткая проверка только у вело сб/вс).
6. Только цель по весу; умных весов нет — `get_body_composition` не берём.
7. `coach goal` — в этом шаге.
8. Мини-спайк — оркестратор.

Спайк `get_user_profile()` (2026-10-07, обезличенная фикстура `tests/fixtures/garmin/user_profile.json`): `userData.gender` = `MALE`/`FEMALE`; `birthDate` = `YYYY-MM-DD`; `weight` — граммы (float); `height` — см (float); `activityLevel` = null (не заполнен — ключ ручной); `vo2MaxRunning`/`vo2MaxCycling` = null (VO2max брать из `get_max_metrics` или не брать); `lactateThresholdHeartRate` есть (LTHR уже берётся в шаге 7); `availableTrainingDays` — список дней (`SUNDAY`…, порядок произвольный) — можно подставлять как начальное расписание, ручное главнее; `preferredLongTrainingDays` пуст; `userSleep.sleepTime`/`wakeTime` — секунды от полуночи. Max HR в user-settings нет — из зон (шаг 7).

Детальный план — [step11-profile-plan.md](step11-profile-plan.md).

Проверка по деньгам (кабан-тесть, 2026-10-07): ок — по подписке $0, в API-эквиваленте сессия ~$0.25 → ~$0.27. Сокращения тестя приняты пользователем («окей, кабаним»): snapshot.profile — только текущие значения и активные цели (история — `get_profile`); сценарий опроса — в отдельном файле, читается только при непустом `missing`; `coach profile show` и итог `coach sync` — коротко.
