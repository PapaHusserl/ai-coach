## Тесты (кабан-доеба)

- add «Купить X» `--note n` в пустой/отсутствующий файл → файл создан, запись id=1, state todo, created=updated=сегодня,
  note n; вывод `+ #1 Купить X` (формат вывода — Р3). Ожидание, не проверено.
- add в файл с id 3, 7 → новый id 8 (max+1, дыры не заполняются, как todo.py).
- start/done/drop/reopen по таблице MOVES: каждое разрешённое → state и updated=сегодня; запрещённое
  (done→doing, dropped→done, doing→doing) → ненулевой код, текст «Нельзя done -> doing (можно: todo)», файл не тронут.
- id нет → ненулевой код, «Нет задачи #N», файл не тронут.
- битый JSON / корень не список → `TodoError`, файл не перезаписан (важно: запись не должна затереть чужой файл).
- запись сохраняет чужие поля записи и записи-не-словари как есть (todo.py их не создаёт, но читать без потерь).
- формат файла: `json.loads` результата == ожидаемому; `ensure_ascii=False` (кириллица не `\u`), indent=1.
- edit `--title`/`--note` → поле меняется; `updated` — по Р4.
- совместимость: файл после `coach todo add` читает `todo.py list --all` — руками в партии (тест в репо на файл из
  `~/.claude` не опирается).
- `read_todo` после done сегодня → `todo_closed` за сегодня +1 (связка с sync).
- `test_every_cli_command_is_in_help` — новые 6 команд в справке.
- Руками: `uv run coach todo add "проба" ; uv run coach todo list ; uv run coach todo drop <id>` на копии файла.

## Развилки и риски

- **Р1. Как писать файл.** (А) своя запись в `workload/todo.py` по той же модели (MOVES и формат скопированы из
  todo.py, ссылка в докстринге), запись атомарно: tmp в том же каталоге + `os.replace`; (Б) вызывать
  `python3 ~/.claude/skills/whats-up/todo.py` подпроцессом; (В) импортировать todo.py по пути.
  Рекомендую А: тестируется без `~/.claude`, путь из coach.toml, ошибки — `fail` вместо `sys.exit` скила, атомарная
  запись не оставит полфайла. Цена — две копии MOVES; расхождение ловится только руками (риск ниже). Б/В — зависимость
  тренера от скила вне репо, `todo.py` нет `edit`, тесты зависели бы от `~/.claude`.
- **Р2. Подтверждение перед записью (видно Владу).** (а) add/start/done/reopen/edit — сразу по слову Влада, без
  переспроса; drop — тоже сразу (обратимо через reopen); после записи тренер показывает строку результата;
  (б) всё после «да» на показанный список; (в) смешанно: сразу всё, кроме drop. Рекомендую (а) — задача пункта
  как раз в том, чтобы не делегировать; всё обратимо. В вечернем ритуале (4а) при (а) тренер показывает список
  пунктов, которые запишет, и пишет после «да» одним заходом (это пункты, сформулированные тренером, не словами Влада).
- **Р3. Вывод команд (видно).** (а) как todo.py: `+ #8 Название`, `#8 -> done`; (б) строка `id  state  title`
  как в `todo list`. Рекомендую (а) — Влад привык к нему по whats-up.
- **Р4. edit и `updated` (видно в сводке).** `read_todo` относит закрытый пункт ко дню `updated`; правка закрытого
  пункта с `updated`=сегодня перенесёт его закрытие на сегодня в `todo_closed`. (а) edit не меняет `updated`;
  (б) меняет. Рекомендую (а). Альтернатива — запретить edit закрытых.
- **Р5. План дня ставит doing (видно).** (а) да: после выбора задач в coach-day тренер выполняет `start` для взятых
  в день пунктов; (б) нет, план дня только читает. Рекомендую (б) в этом шаге — минимум под пункт; (а) — если Влад хочет.
- **Р6. `todo list --all` (видно).** Добавить флаг, чтобы тренер мог найти закрытый пункт для reopen? Рекомендую да
  (одна опция, нужна для reopen по названию); иначе reopen только по id, который Влад назовёт.
- Риск: одновременная запись whats-up и тренера — гонка «прочитал–записал» теряет пункт. todo.py не блокирует,
  поэтому блокировка с нашей стороны не защитит; на практике пишет один человек за раз. Принять, в бэклог — нет.
- Риск: расхождение моделей при правке todo.py (новое поле, новый state). Читатель терпим к лишним полям; новый
  state сломает MOVES тренера громко (KeyError → ошибка). Принять; находка ниже.
- Риск: `coach-evening` п. 4а сейчас запрещает писать в туду — без правки 4а тренер продолжит отсылать к Владу.
