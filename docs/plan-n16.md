# Н16. История импорта: пульс покоя и HRV (BACKLOG 30, 29, 33, 32)

Срок: до 2026-11-10 (дальше v2.9 ждёт данных за 2026-11-10…17). Архитектор, 2026-11-01. Контур: вне msa; режим:
встроить.

## Суть

Импорт zip-экспорта Garmin (`coach import`, даты до 2026-09-30) кладёт в `daily_metrics` другой словарь, чем API
(с 2026-10-01). Три места кода этого не знают: пульс покоя (`last_rest_hr`), плохой HRV (`find_deviations`),
коридор HRV Garmin. Шаг учит их читать историю импорта, чтобы `get_load`, TSS и отклонения работали на датах
до 2026-10-01 (нужно Н6/Н9 и калибровке v2.9).

**Правило:**

1. `store/garmin_data.py:129 last_rest_hr` — было `json_extract(raw_json, '$.sleep.restingHeartRate')` → станет
   `COALESCE(json_extract(raw_json, '$.sleep.restingHeartRate'), <value метрики HR из $.hrv.metrics>)` (то же
   выражение, что уже в `list_recovery_days`, `garmin_data.py:43-48`) — при Р2 = 1.
2. `load/deviations.py:9` — было `BAD_HRV_STATUSES = ("LOW", "UNBALANCED")` → станет
   `BAD_HRV_STATUSES = ("LOW", "UNBALANCED", "BELOW")` — при Р1 = да.
3. BACKLOG 33 — новое: функция чтения коридора HRV Garmin из `raw_json` обоих источников — при Р3 = 1.

**Поведение:** меняется только на датах до 2026-10-01: `get_load`/`get_plan_actual`/недельный обзор считают TSS
вместо «нет свежего пульса покоя»; `get_deviations` за такую дату показывает `hrv` при BELOW. Сегодняшние ответы
(данные API) не меняются: API не отдаёт BELOW и всегда имеет `restingHeartRate`.

**Вне репо:** нет. Allow-строк не нужно: новых команд CLI нет.

## Разведка на живой базе (2026-11-01, без личных цифр)

Проверено `sqlite3 -readonly ~/.local/share/ai-coach/coach.db`:

- `hrv_status` импорта **уже пишется** (`export_days.py:40`): IN_RANGE 266, BELOW 19, ABOVE 9 строк
  (2025-12-10…2026-09-30); у API — BALANCED/UNBALANCED/LOW. Совпадение колонки с `metrics[type=HRV].status` —
  0 расхождений. Текст BACKLOG 33 «не пишет `hrv_status`» неверен (см. Побочные 1).
- `hrv_weekly_avg` у импорта взять неоткуда: в `_healthStatusData.json` поля недельного среднего нет (ключи
  элемента: `calendarDate`, `metrics[]`, `outliersCount`, таймстампы). У API — 32 строки с 2026-10-01.
- Метрики импорта: HR, HRV, RESPIRATION, SKIN_TEMP_C, SPO2 — по 294 строки; у каждой `value`,
  `baselineLowerLimit`, `baselineUpperLimit`, `status`, `percentage`, `feedbackKey`.
- Коридор API — `$.hrv.hrvSummary.baseline` {`lowUpper`, `balancedLow`, `balancedUpper`, `markerValue`}, 32
  строки; уже лежит в `raw_json`, колонок нет.
- Пульс покоя: API `$.sleep.restingHeartRate` — 32 строки (2026-10-01…11-01); импорт — `metrics[type=HR]` 294
  строки (2025-12-10…2026-09-30). Перекрытия нет. В сне импорта полей пульса нет.
- BACKLOG 32 (расхождение ~10 %): среднее HR импорта за сентябрь выше среднего `restingHeartRate` API за октябрь
  на 9,8 %; на днях API средний пульс сна (`sleepHeartRate[]`) выше `restingHeartRate` на 7,9 % (32 дня).
  Вывод: HR Health Status — скорее **средний пульс за ночь**, а не пульс покоя Garmin (минимум 30 мин за сутки).
  Это гипотеза по косвенному признаку, перекрытия для прямой сверки нет.

## Развилки и риски

**Р1. BELOW = плохой HRV** (видимое: отклонение в `get_deviations` за историю). (да) BELOW → `hrv`; (нет) история
импорта без HRV-отклонений, как сейчас. Рекомендую «да»: BELOW — «ниже личного диапазона», ровно смысл LOW; без
этого калибровка v2.9 по отклонениям теряет 19 дней. ABOVE — не считать (высокий HRV плохим не считаем и у API).

**Р2. Пульс покоя для дат до 2026-10-01** (видимое: TSS, CTL/ATL истории, `get_load` перестаёт падать).
(1) HR импорта как есть (COALESCE, как в `list_recovery_days`); (2) HR импорта с поправкой на измеренные −8 %;
(3) не трогать — BACKLOG 30 закрыть как «не пульс покоя» (BACKLOG 32). Рекомендую (1): одно определение уже
принято в `list_recovery_days` (Н11), поправка (2) — подгонка по одному человеку без перекрытия; завышенный
пульс покоя сдвигает IF мало (входит и в числитель, и в знаменатель). Альтернатива (3) честнее по определению,
но оставляет историю без TSS.

**Р3. BACKLOG 33: как хранить коридор Garmin** (внутреннее хранение, но видимо, если выводить в MCP).
(1) Без миграции: новая `list_hrv_corridor` читает `raw_json` обоих источников, в MCP не выводится; (2) миграция:
колонки `hrv_low`/`hrv_high` + заполнение в `garmin_sync` и `add_hrv` + переимпорт; (3) кода нет — пункт закрыть:
всё уже в `raw_json`, v2.9 читает запросом. Рекомендую (1): стиль `list_recovery_days`/`list_sleep_nights`, без
переимпорта; (3) — если Влад хочет минимум, v2.9 всё равно будет писать свой код.

**Р4. Говорить ли пользователю о разнице определений** (видимое: текст справки `training.md`). (да) строка в
справке «до октября 2026 пульс покоя — средний за ночь из экспорта, выше на ~8–10 %»; (нет) молча. Рекомендую
«да» при Р2 = 1: иначе скачок CTL/TSS на стыке 30.09/01.10 не объяснить.

Риски:
- Стык источников 2026-09-30/10-01: пульс покоя прыгает вниз на ~8–10 % — TSS истории чуть ниже реального
  (IF меньше); для калибровки v2.9 — помнить о стыке.
- Коридор импорта (`baselineLower/UpperLimit` Health Status) и API (`balancedLow/Upper` HRV Status) — разные
  отчёты Garmin; что это одно и то же определение, не проверено (перекрытия нет).
- Окно `REST_HR_MAX_AGE_DAYS 14` (`tools.py`): для дат 2026-10-01…10-14 теперь найдётся пульс из импорта, если
  API-строки нет — ожидаемо.
- HRV импорта — float (`value`), колонка `hrv_last_night` INTEGER; `list_hrv_corridor` вернёт границы как в
  JSON (float) — не округлять (Умолчание 2).
